Lesson 1 · Koso Backend

The Two-Layer Backend

Koso's server has two layers that talk to the same two databases. Understanding the split is the single most important idea in this whole project.

Why are there two layers at all?

When we started, the code lived in controllers/ as plain TypeScript classes — no framework. Then NestJS was added as the actual HTTP framework, which requires files to live under src/. So we ended up with both: the original hand-rolled controllers and the "real" NestJS modules.

NestJS is what actually handles incoming HTTP requests. The controllers/ folder is the old layer — it still exists because it was already written, and it can be reused by anything that doesn't go through NestJS. But all the live routes come from src/.

The mental model

Both layers, at their core, do the same thing:

incoming HTTP request
        │
        ▼
   [Route / Decorator]      ← "this URL maps to this method"
        │
        ▼
   [Controller method]      ← "this method needs inputs from the URL/body"
        │
        ▼
   [Service method]         ← "do the actual work"
        │
        ▼
   [Supabase / Paystack]    ← "the real database / payment API"

The controller is a thin layer — it only knows about HTTP. The service is where the logic actually lives — it talks to Supabase. This separation is the heart of NestJS: controllers handle HTTP, services handle data.

The two layers side by side

Aspect controllers/ src/ (NestJS)
Style Plain classes, no decorators Decorators (@Controller, @Injectable)
HTTP routes None — you'd call methods directly Yes — decorators map URLs to methods
DB access Wraps Database class Calls supabase directly
Used by the running server? Not directly — legacy Yes — it's what main.ts boots

How NestJS knows the modules exist

Everything is wired together in src/app.module.ts. When the server starts, NestJS reads this one file to learn the full "map" of your app: 

@Module({
  imports: [
    ClientsModule, ProjectsModule, MeetingsModule,
    LogsModule, PaymentsModule, DocumentsModule,
    MilestonesModule, PaymentLinksModule, TransactionsModule,
  ],
  controllers: [AppController],
  providers: [AppService],
})
export class AppModule {}

If you create a new module and forget to add it here, NestJS will never mount its routes. This file is the front door.

The flow for a real route: GET /clients

  1. main.ts boots AppModule.
  2. app.module.ts imports ClientsModule.
  3. ClientsModule registers ClientsController (the routes).
  4. A browser hits GET /clients → NestJS matches it to @Get() findAll() in the controller.
  5. The controller calls this.clientsService.findAll().
  6. The service runs supabase.from('Clients').select() and returns the rows.
  7. NestJS turns that into a JSON response.
Key insight The bulk of the "work" is a one-liner on Supabase. The controller + service exist to define how and when that one-liner runs. Don't overestimate the complexity — most services are thin wrappers over a Supabase call.

How each piece fits in a file

Here's a real service method from src/clients/clients.service.ts:

async findAll() {
  const { data, error } = await supabase.from('Clients').select();
  if (error) throw new BadRequestException(error.message);
  return data || [];
}

NestJS (via @nestjs/common) gives us the BadRequestException so a failed DB call returns a clean 400 HTTP error instead of crashing.

How to read a DTO

A DTO (Data Transfer Object) is just a TypeScript class describing the shape of the data a request body must have. It's validation and documentation in one. 

// src/clients/dto/create-client.dto.ts
export class CreateClientDto {
  email: string;
  first_name: string;
  last_name: string;
  phone: string;
}

The service takes one of these as input. If you ever change a table's columns, the DTO tells you exactly what the API expects — they should match.

Your turn — 3 quick checks

Quiz: What does the controller know that the service does not?
  • A: The Supabase table name
  • B: The HTTP route and request inputs
  • C: How to format currency

Answer: B. The controller owns the HTTP concerns (URL, params, body). The service owns the data access.

Quiz: You add a new module UsersModule. What else must you touch for its routes to work?
  • A: Nothing — it's automatic
  • B: src/app.module.ts — add it to imports
  • C: main.ts — add it there

Answer: B. app.module.ts is the wiring map. Without it, the routes never mount.

Quiz: If supabase.from('Clients').select() succeeds, what does the service return?
  • A: The raw { data, error } object
  • B: Just data (or an empty array)
  • C: Nothing — it throws always

Answer: B. The service destructures { data, error } and returns data || [].
